# Plan 4 — Claude's ears: analysis, spectrograms and reference comparison

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Claude can "hear" a passage without the GUI. `tune analyze` measures loudness, peaks, band balance, brightness, stereo and per-section energy of a render or any audio file, and draws a labelled spectrogram PNG that Claude reads as an image. `tune compare` sets our passage against the producer's reference track and states the differences in plain words. `tune refs` lists the references configured outside git.

**Architecture:** A new headless crate `tune-analysis` takes planar audio (`Audio`) plus an optional bar map (`BarMap`) and returns plain structs with a stable JSON form. It does not depend on `tune-song` or `tune-engine`, so a reference MP3 and our render go through the same code. `tune-cli` glues it to songs: it renders a song or bar range in memory with `tune_engine::render`, builds the `BarMap` from the compiled song's clock and sections, resolves reference names from a gitignored `tune.local.toml` or `refs/` folder, and writes PNGs (by default into `scratch/`). No MCP server: the CLI with `--json` and PNG files is the whole interface (producer's decision).

**Tech Stack:** Rust 2024 (toolchain 1.97). New dependencies, all in `tune-analysis` only: `ebur128 =0.1.10` (EBU R128 / BS.1770: integrated, short-term, LRA, sample and true peak), `symphonia =0.5.5` (`default-features = false`, features `mp3`, `aac`, `isomp4`, `flac`, `pcm`), `realfft =3.5.0` (STFT), `png =0.18.1` (encoder), `font8x8 =0.3.1` (8×8 bitmap glyphs for labels), `hound 3.5` (WAV), `serde_json 1` (`preserve_order`), `thiserror 2`. `tune-cli` adds `tune-analysis` and `toml =1.1.2` (same features as `tune-song`). Test-time tools, not dependencies: macOS `afconvert` (AAC, FLAC fixtures) and `lame` if installed (MP3 fixture).

**Spec:** `docs/superpowers/specs/2026-10-20-tune-ai-design.md`. This plan covers §1 "Why it matters", G5 (analyse and compare without the GUI, via CLI), §6.5 `analyze` and `compare`, §6.6, §5 privacy for reference tracks, and §8 "Analysis sanity". It does not build `tune-mcp` (the producer chose CLI only). Plans 1–3 must be complete; this branch builds on their `tune_engine::{render, RenderOptions, Rendered, CompiledSong, Clock}`, `tune_song::load_song`, and `tune-cli`'s `report::{finish, Success, Failure, parse_bar_range, fmt_time, dbfs}` and `cmd::{load, sample_rate}`.

## Global Constraints

- macOS on Apple Silicon only. Repo stays MIT. No GPL code copied.
- Branch `feat/ears`, stacked on `feat/studio-ui`. Atomic conventional commits, one concern each. Run `task verify` before every commit.
- Never commit audio, spectrogram PNGs, renders, `tune.local.toml`, anything under `refs/`, or `scratch/`. Reference tracks live outside git. No absolute home paths, emails, real names or machine-specific data in committed files; docs use `~/…` placeholders. The privacy check stays green and is never weakened to pass.
- `tune-analysis` is headless: no `cpal`, `tokio`, `axum`, `tauri`, `tune-engine` or `tune-song` dependency, and `#![forbid(unsafe_code)]`. `tune-dsp`, `tune-song`, `tune-engine`, `tune-studio` are unchanged.
- Determinism: the same input gives the same numbers and the same PNG bytes. No threads in analysis, no `HashMap` iteration in output, sums in a fixed order and accumulated in `f64`, no timestamps or text chunks in PNGs.
- Analysis runs at the file's own sample rate; nothing is resampled. Frequencies are in Hz, so a 44.1 kHz reference and a 48 kHz render line up.
- Genre targets (acid techno, spec §6.6): integrated −8 to −6 LUFS, true peak ≤ −1 dBTP.
- Bars: 1-based and inclusive in CLI flags, text and JSON; `BarMap`/`SectionSpan` and the engine use 0-based bars.
- CLI conventions hold: every command takes `--json`, exit 0 on success and 2 on failure, JSON on stdout (via `report::finish`), text errors on stderr. JSON keys are stable; adding a key is allowed, renaming or removing one is a breaking change that needs a doc update.
- JSON numbers: dB, LU, LUFS, octaves and correlations rounded to 2 decimals, Hz to 1 decimal. A quantity that does not exist (silence, too short) is `null`, never `NaN` or `-inf`. Peaks and side/mid on silence use the existing `-200` floor (`report::dbfs` convention); band levels floor at −120 dB.

## Decisions made in this plan (flag if wrong)

- **WAV through `hound`, everything else through `symphonia`** (gapless trimming on). Files with more than two channels are rejected rather than downmixed. Mono is measured as dual mono (`ebur128::Channel::DualMono`), so a mono file reads like the same signal on two speakers.
- **One STFT for all spectral numbers:** Hann window, size `((sr * 0.085) as usize).next_power_of_two()` (4096 at 44.1 and 48 kHz), hop = size / 4, frames fully inside the signal (one zero-padded frame if the signal is shorter). Power per bin is `|L|² + |R|²` (mono: `|X|²`), so anti-phase content still counts. Spectrum normalised so a full-scale sine's bin peak reads 0 dB.
- **Bands** cover 20 Hz–20 kHz (capped at Nyquist): `sub` 20–60, `low` 60–250, `low_mid` 250–1k, `mid` 1k–4k, `high` 4k–12k, `air` 12k–20k, each as dB relative to the 20 Hz–20 kHz total. Relative levels do not move with gain, so loudness and balance are separate questions.
- **Low-end check:** `kick_region_db` (20–90 Hz) and `bass_region_db` (90–250 Hz) relative to total, and `ratio_db` = kick − bass. 90 Hz follows the research (the 303 lives from ~85 Hz up, the kick owns the sub). Plus `stereo.low_correlation`: L/R correlation below 120 Hz from the STFT cross-spectrum, because club low end must be mono.
- **Time series on a 1 s grid:** entry `i` covers second `[i, i+1)`. `short_term_lufs[i]` is the 3 s window ending at `i+1` s (`null` for `i < 2`). `centroid_hz[i]` is the power-weighted centroid of that second's summed spectrum, `null` when its RMS is below −80 dBFS.
- **Brightness trajectory** is compared through `median_hz`, `p10_hz`, `p90_hz`, `range_oct = log2(p90/p10)` (how far the filter moves) and an 8-point `profile_hz` (median centroid of each eighth of the duration), because a passage and a whole reference have different lengths.
- **Onset density is left out** (YAGNI): 16th-note hats make it noisy and files carry no tempo.
- **Spectrogram colours are absolute** (−100 dB darkest, −20 dB brightest, magma-style ramp), so a quieter mix looks darker next to the reference. The band strip under it shows each band's share of that column's total (−40..0 dB). Labels use `font8x8` at 2× (16 px), ASCII only (other characters draw as `?`).
- **Compare PNG stacks the two panels vertically** (ours on top) with the same frequency axis and colour scale; each keeps its own time axis.
- **References:** `tune compare <ours> <path>` or `tune compare <ours> --ref <name>`, exactly one. Names come from `[refs]` in `tune.local.toml`, then from files in `refs/` (name = file stem). The root is the nearest ancestor of the current directory (inclusive) that holds `tune.local.toml` or a `refs/` directory. `~/` expands from `$HOME`; relative paths resolve against the root.
- **`--ref-seconds A..B`** trims the reference, so a drop can be compared with the reference's drop. **`--song` + `--from-bar N`** map a WAV onto a song's bars, mirroring `tune play --from-bar`.
- **Bare `--png`** writes `scratch/<stem>[-bars-A-B].png` relative to the current directory (`<stem>` is the song's `name` for a song input, the file stem otherwise; compare: `scratch/compare-<ours stem>[-bars-A-B]-vs-<ref stem>.png`). `--png <path>` writes there.
- **Privacy check** additionally blocks `.aac`, any file named `*.local.toml`, any path under `refs/`, and image files (`png`, `jpg`, `jpeg`, `gif`, `webp`) outside `apps/desktop/src-tauri/icons/`.
- **`symphonia` pinned to 0.5.5**, the widely documented API; moving to 0.6 is its own later commit.

**Files:**
- Create: `crates/tune-analysis/src/spectral.rs`, `crates/tune-analysis/tests/spectral.rs`

**Interfaces:**

- Produces:
  ```rust
  pub struct Band { pub key: &'static str, pub label: &'static str, pub lo_hz: f64, pub hi_hz: f64 }
  pub const BANDS: [Band; 6];   // sub/"sub" 20-60, low/"low" 60-250, low_mid/"low-mid" 250-1000,
                                // mid/"mid" 1000-4000, high/"high" 4000-12000, air/"air" 12000-20000
  pub(crate) struct Frame<'a> { pub index: usize, pub center_frame: usize, pub power: &'a [f64],  // |L|²+|R|², normalised
                                pub left: &'a [Complex<f64>], pub right: &'a [Complex<f64>] }    // right == left for mono

  #[derive(Clone, Debug, PartialEq)] pub struct Stereo { pub correlation: Option<f64>, pub side_to_mid_db: f64, pub low_correlation: Option<f64> }
  #[derive(Clone, Debug, PartialEq)] pub struct Brightness {
      pub centroid_hz: Vec<Option<f64>>,   // 1 s grid
      pub median_hz: Option<f64>, pub p10_hz: Option<f64>, pub p90_hz: Option<f64>, pub range_oct: Option<f64>,
      pub profile_hz: [Option<f64>; 8],    // median centroid of each eighth of the duration
  }
  #[derive(Clone, Debug, PartialEq)] pub struct Spectral { pub bands: [Option<f64>; 6], pub low_end: LowEnd, pub stereo: Stereo, pub brightness: Brightness }
  pub fn measure_spectral(audio: &Audio) -> Spectral;
  ```
- Band, region and centroid sums use bins whose centre is inside `[lo, hi)` and inside 20 Hz–`min(20 kHz, Nyquist)`. A band is `None` only when the total is zero; otherwise floored at −120 dB. `correlation = ΣLR / sqrt(ΣL² ΣR²)` over the whole signal (time domain, `None` when either side is silent; mono gives 1.0). `side_to_mid_db = 10·log10(ΣS²/ΣM²)` with `M = (L+R)/2`, `S = (L−R)/2`, floored at −200. `low_correlation = Re Σ L·conj(R) / sqrt(Σ|L|² Σ|R|²)` over bins below 120 Hz. Percentiles are nearest-rank over the `Some` centroids. Each frame is assigned to the second containing its centre frame.

**Files:**

**Interfaces:**

  #[derive(Clone, Debug, PartialEq)] pub struct SectionSpan { pub name: String, pub start_bar: u32, pub bars: u32 }  // 0-based song bars

      pub partial: bool, pub integrated_lufs: Option<f64>, pub short_term_max_lufs: Option<f64>,
      pub delta_lu: Option<f64>,       // vs the previous reported section

  pub fn analyze_sections(audio: &Audio, map: &BarMap) -> Result<Vec<SectionReport>, AnalysisError>;
  pub const ACID_LUFS: (f64, f64) = (-8.0, -6.0); pub const TRUE_PEAK_MAX_DBTP: f64 = -1.0;
  #[derive(Clone, Debug, PartialEq)] pub struct Targets { pub integrated: &'static str, pub true_peak: &'static str }
  pub fn classify_targets(integrated_lufs: Option<f64>, true_peak_dbtp: f64) -> Targets;
  #[derive(Clone, Debug, PartialEq)] pub struct Analysis {
      pub sample_rate: u32, pub channels: u16, pub seconds: f64, pub loudness: Loudness,
      pub short_term_lufs: Vec<Option<f64>>, pub spectral: Spectral, pub targets: Targets,
      pub sections: Option<Vec<SectionReport>>,

  pub fn analyze(audio: &Audio, sections: Option<&BarMap>) -> Result<Analysis, AnalysisError>;
  impl Analysis { pub fn to_json(&self) -> serde_json::Value; pub fn summary_json(&self) -> serde_json::Value; }
