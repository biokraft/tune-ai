# Plan 7: Model v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the closed instrument and effect enums with a module registry, give tracks devices with ids, move patterns into a clip pool, arrange clips as per-track placements under named sections with automation as lane stretches, and introduce song format v2 with a comment-preserving migration from v1, while every v1 song renders bit for bit as before and the current studio keeps working.

**Architecture:** A new `tune-modules` crate holds the instrument and effect traits, today's eight modules and the registry; its descriptors carry both the param tables the validator reads and the factories the engine calls. The song model changes in place, one concept per task (devices, clips, arrangement), while the file format stays v1, so the existing v1 parse tests and the render pins guard every step. Format v2 is then added to the same reader, a `toml_edit` migration rewrites v1 text, and finally the studio edits v2 text and the UI shows v2 content (read-only where it cannot edit it).

**Tech Stack:** Rust 2024 (workspace), `toml` =1.1.2, `toml_edit` =0.25.17 (now also in `tune-song`), `indexmap` 2.14, `rtrb` =0.3.4, React 18 + TypeScript + Vitest in `apps/desktop` and `packages/ui`. No new third-party dependencies.

**Spec:** `docs/superpowers/specs/2026-10-26-phase-2-modular-model-design.md` (the authority). This is the first of four Phase 2 plans; it covers §7.1 (minus the crossfade), §7.2, §7.4 (303 and drum clips only), §7.5, §7.7 and §10. Out of scope, for later plans: note clips, the note-event instrument API and the 10 ms structural-swap crossfade (Plan 8); the action layer, `tune actions`/`tune do`, CLI routing to a running studio, generated TS types, structured undo, runs, ⌘Z and "Undo this run" (Plan 9); scenes, slots and the session engine (Plan 10).

## Review Focus

1. **Comments in the places the migration rewrites.** A comment above or after a section's `play = {…}`, above `[[sections.automation]]`, above `track = "…"` in a pattern, or inside a track table: every comment line of the v1 file is still in the v2 file, in order. (Task 6 `migration_keeps_every_comment_in_order`, `keeps_comments_on_removed_play_keys`.)
2. **A placement that crosses a section edge**, with a non-zero offset, then moved, duplicated, resized or deleted from the UI: it is split at the edge first, and every step outside the edited section plays the same clip step as before. (Task 8 `ops_keep_steps_outside_the_edit`.)
3. **A second EQ (`eq2`) the agent added by hand.** `tune set tracks.acid.eq2.low_cut=200` and a lane on `acid.eq2.low_cut` reach that device and no other; the dock lists it by name without knobs and nothing crashes. (Task 9 `set_param_on_second_eq`, Task 10 `lists a second eq by name without knobs`.)
4. **Undoing the migration, or a read-only song folder.** Undo after open puts the v1 bytes back and the studio keeps working; the next edit writes v2 again. If the write-back fails, the song still opens (migrated in memory) and the producer sees an error. (Task 9 `open_v1_migrates_writes_logs_and_can_undo`, `open_v1_in_a_readonly_dir_still_opens`, `edit_after_undoing_the_migration_writes_v2_again`.)
5. **An incompatible clip or a typo'd module from the agent.** `tune set sections[0].play.acid=kick4` or `instrument = "acid3030"` fails with a positioned message naming what is allowed, and the file is untouched. (Task 5 `device_rules`, `placement_rules`; Task 9 `set_section_play_rejects_an_incompatible_clip`.)

## Format v2 (decided)

Every name here is binding for all tasks.

```toml
[song]
version = 2                        # required in v2; absent (or 1) means v1; anything else is rejected
name = "first-acid"
bpm = 145
seed = 1
sample_rate = 48000

[mix]                              # unchanged from v1
master = "limit"
params = { "master.gain" = 8.5 }

[tracks.acid]
instrument = "acid303"             # a module name: device id = the module name
# or: instrument = { type = "acid303", id = "bass" }   (table form: `type`, optional `id`, the module's settings)
gain_db = -2                       # pan, mute, solo unchanged
params = { "acid303.cutoff" = 350, "send.delay" = -16 }   # instrument params `<instrument id>.<param>` + strip params
fx = [
  { type = "eq", params = { "eq.low_cut" = 85 } },                 # id defaults to the module prefix
  { type = "eq", id = "eq2", params = { "eq2.mid_gain" = 3 } },    # a second instance needs an explicit id
  { type = "distortion", mode = "soft", params = { "dist.drive" = 24 } },
]
play = [                           # placements: in time order, never overlapping
  { at = 17, clip = "acid_main", bars = 16 },                      # at = 1-based start bar
  { at = 33, clip = "acid_main", bars = 32, offset = 4 },          # offset = bars into the clip (default 0)
]

[clips.acid_main]
kind = "acid"                      # "acid" (303 notation) or "drum" (x X .); Plan 8 adds "notes"
steps = "C2 C2! C3~ C2 . D#2 C2~ G2! . C2 C3 C2~ A#1 C2! . F2~"

[[sections]]                       # named regions laid end to end from bar 1; they set the song length
name = "intro"
bars = 16

[[automation]]                     # one stretch of one param's lane
param = "acid.acid303.cutoff"      # `<track>.<device>.<param>`, `<track>.send.delay`, `mix.<param id>`
at = 17                            # 1-based start bar
bars = 16                          # outside every stretch of a param, the param plays its static value
points = [[0, 0.02], [16, 0.12]]   # [bar offset from `at`, normalized 0..1]
```

Rules:
- Device ids match `[a-z0-9_]+`, are unique within a track (instrument included) and may not be `send` or `duck`. Default id: the module's `prefix` (equal to the name for instruments). A file names `id` only when it differs from the prefix. The add-device default for a repeat is `<prefix>2`, `<prefix>3`, … (`Track::next_device_id`).
- Every key in a `params` table is a track-relative param id: `<device id>.<param>`, or a strip id in the track's own `params`. Lanes, `tune set` paths and studio knobs use the same ids, so v1 ids stay valid.
- Device settings (today only the distortion `mode`) are keys of the device's table. The model stores every setting filled in; the canonical writer writes them all.
- `play`, `at`, `bars`, `offset` are whole numbers in Plan 7. `[[automation]]` stretches of one param may touch but not overlap; any number of stretches per param, any order in the file.
- `[[automation]]` tables may sit between `[[sections]]` tables (the migration puts each section's stretches right after it); the canonical writer puts them all after the last section.
- Placement formatting (canonical writer, migration and studio alike): one placement is written inline, `play = [{ at = 3, clip = "a1", bars = 2 }]`; two or more one per line with two-space indent and a trailing comma. A track with no placements has no `play` key.
- Clip compatibility comes from the instrument's descriptor: `acid` clips play on modules whose `plays` has `Acid`, `drum` clips on `Drum`.

  v_at   = lane_value(P, k)                    // the engine's rule: later point wins on equal bars
  v_left = first value of a point with bar == k, if any, else v_at
  left   = (s, k,     [points of P with bar < k] ++ [(k, v_left)])
  right  = (b, n - k, [(0, v_at)] ++ [(bar - k, v) for points of P with bar > k])
